## Decisions and prerequisites

The owner accepted both recommendations on 2026-10-24. An ordinary query
advances the statement index, so weak output translation alone does not lift
across a clock-sensitive migration. Every full-state pair needs the contextual
commuting condition, and restricted simulation preserves its domain after calls.
Weaker query-output claims remain separately available. The later accepted
scoped relation requires explicit context/observation scope and per-call closure,
with actual-run agreement and bidirectional matching of all branch outcomes.
The positive expansion theorem uses that relation. Native equal-row orders
have total_changes 3 versus 4, so the full-state counterexample remains required.
Counter/clock-sensitive interface calls must meet the same call conditions.

The constructive application representation must retain call identity and
arguments; raw Sql syntax has no unique decomposition into interface calls.
This is an implementation constraint, not a change to SQL execution. Public
primitives retain explicit witnesses for ambiguous convenience cases.

The original task said that no S6 production module existed. At `28174c12`
these are present: execution branches, success and equivalence; the migration

`expansion_state`) with the retained counter refutation; S4 run laws; S5
certified search and replay. The task now lists each reused interface under its
own heading, so an implementer does not rebuild one.

Corrections to the original text:

- The task said that the prerequisites "must be integrated before implementation".
  They are integrated. That sentence is removed.
- The task did not say that the model has no exact effect law for a write that
  fires a trigger. It has only plain-write laws (`PlainInsertEffect`,
  `PlainDeleteEffect`) and invariant-preservation theorems. The expansion
  outcome needs exact laws for INSERT and UPDATE under `AFTER` triggers. The
  task now names this as required work and as the largest cost.
- S5 replay refuses a clock or counter read. A call that reads `total_changes()`
  therefore has kernel and native-SQLite evidence, as the counter fixture has,
  and no S5 replay.
- The S6 automation task (certified effect rules, `sql_commute`) is not done.
  The automation outcome is limited to S5 search, the automatic theorem check
  and `#explain`.

Waiting items. Migration-patterns part 2 (rebuild cascade, safe rebuild,
affinity) waits for the table-rebuild task. No S8 outcome needs those
examples, because the reverse-direction counterexample uses CREATE TABLE,
DROP TABLE and DROP TRIGGER, which the model has. No S8 outcome is marked as
waiting for that task. DROP COLUMN and RENAME are not in the model; the
task needs neither.

No contradiction was found between the task, ADR 0017 and the code.
