## Outcome

1. **Joined sources.** A `SELECT` reads a `FROM` list of table references, joined left
   to right with `,`, `JOIN`, `INNER JOIN`, `CROSS JOIN` (optional `ON`) and
   `LEFT [OUTER] JOIN` (with `ON`). A table reference has an optional alias. The rows
   are the cartesian product filtered by `ON`; a left join adds each unmatched left
   row with NULL in every right column. `WHERE`, groups, aggregates, projection,
   `ORDER BY` and the window then work on the joined rows as for one table.
2. **Names.** As the amendment's "Names" says: qualified names `x.c`, unqualified names
   that must name exactly one column (`ambiguous column name: c`), an alias hides the
   table name, `no such column: x.c`, `*` and `x.*` (`no such table: x`), qualified
   bare columns named by their column name, and the same rules in every clause.
3. **Errors and restrictions.** SQLite's prepare errors above and
   `at most 64 tables in a join`. Model restrictions, with byte ranges and registry
   ids, examples and documentation rows: `USING`, `NATURAL`, `RIGHT` and `FULL` joins,
   two sources with the same name, subqueries and table-valued functions in `FROM`,
   and the rowid names of a joined table (as for one table).
4. **Verification target.** Queries change no state; writes keep one table. The
   execution semantics, `statementReady` and `Contract.lean` do not change.
5. **Evidence.** Authored coverage cases of the amendment's "Testing" list agree with
   native SQLite and have kernel proofs; the mutants of that list each change a
   verdict; the verdict counts of the claimed corpora do not go down.

## Tests

- Frontend mapping of each join form, aliases, qualified names and `x.*`, with byte
  ranges, and refusal of the forms outside the slice.
- Lean examples and proofs: the single-table query is the case with no joins and keeps
  its results; a joined row has the sum of the widths of its tables; a left join keeps
  every left row at least once.
- Authored coverage cases and mutants as listed in the amendment's "Testing".
- The restriction registry, example and mutant link tests with the new restrictions.

## Key points for the implementer

- **The query form.** `Resolved.Query` holds one `table : Nat` (`Resolution/QueryForm.lean`).
  `Query.run` and `Query.fails` (`QueryEval.lean`), `Outputs.statementOutput` and
  `Execution.step` read one table. The source becomes a first table and a list of
  joins; expressions keep `Expr.column` positions, now into the concatenated row.
  `QueryLaws.lean` and the slice 1 and 2 examples state results over one table.
- **Resolution.** `Resolution/Queries.lean` (175 lines) and `QueryExprs.lean` (182)
  resolve names against one table's columns (`columnPosition`); names now resolve
  against a list of named sources with column offsets. Put the source resolution in a
  new module. The `RETURNING` and write resolution (`Returning.lean`, `Updates.lean`,
  `Deletes.lean`) keep one table and must keep their behavior.
- **Syntax and frontend.** `Syntax.Statement.select` has `table : String`;
  `Syntax.Expr.identifier` has no qualifier, and `Syntax.ResultColumn` has no `x.*`.
  `belay/sqlite/syntax_queries.py` is at 197 lines and refuses joins, aliases and
  `table.*` today; put the `FROM` mapping in a new module. The syntax JSON of
  existing statements should not change where it can stay the same.
- **Kernel cost.** Kernel proofs evaluate the cartesian product; keep authored cases to
  two or three tables with a few rows each.
- **Mutant cost.** The mutant suites are near their time limits on the hosted runner;
  measure them after adding mutants, and split a measurement if needed.
