# S5: checked counterexamples for SQL claims

Created 2026-10-24. Status: OPEN. S4 is complete; implementation follows handoff review.
Status: [status file](20261024-surface-s5.status.md).
Specifications: [ADR 0017](../docs/adr-0017-user-surface.md), D1, D4 and D6;
[ADR 0016](../docs/adr-0016-model-and-surface.md), D2.
Target: the product guide's "Check before you prove", "Counterexamples for any
statement", `sql_refute`, and open questions 16 and 18.
The guide is `model-user-guide.md` in `vihren-dev/sqlite-verifier-product`,
inspected at commit `5dbc6f15f92db211a67edc39a08ffede625f0d11`.
The required S5 behavior from that guide is restated below.

## Scope and owner decisions

S5 gives the user a checked answer before a universal proof: a proof, a concrete
counterexample, or an explicit unknown result. The claim keeps its original
meaning. A finite search is never evidence that a universal claim is true.
S4 supplies query propositions, success propositions and their laws. S6 later
supplies triples, equivalence, footprints and the complete `sql_auto` tactic;
S5 must leave the search usable for those propositions without implementing them.

Decided by the owner on 2026-10-24:

- Infer small candidate schemas and targeted values from SQL by default, and
  also expose explicit schemas and custom generators.
- Enable background checking by default. Only a kernel-confirmed counterexample
  is an error. The budget is configurable and its default is chosen from a
  measurement in the pinned environment.

## Required outcomes

1. **One checking operation.** `#sql_check P` accepts a Lean proposition. It first
   tries available proof automation, and otherwise searches for a counterexample.
   It reports proved only with a kernel-checked proof of `P`, false only with a
   kernel-checked proof of `¬ P`, and unknown otherwise. A missing sampling
   instance, exhausted budget, rejected candidate, unsupported claim shape or
   failed certification never becomes a proof or a reported false claim.
   The command does not add an admitted theorem to the environment.
2. **Explicit and searched refutation.** In a goal `¬ P`, `sql_refute` runs the
   same search and closes the goal only with a kernel-checked refutation.
   `sql_refute (db := db! r"...")` checks the supplied database. Named parameter
   values and the environment inputs required by the claim can also be supplied.
   Incorrect witnesses fail with a diagnostic and leave no admitted proof.
   Users can call the checking primitives with their own candidates without
   reverse-engineering the notation or the default generator.
3. **Valid, useful samples.** The database sampler produces values of the
   bundled `Database` with checked validity. Its default candidates use the
   table/column names and constants of SQL visible in the claim, small schemas
   and row sets, and targeted NULL, integer-boundary and text values. It can find
   duplicate values under `NOCASE`, ASCII/non-ASCII case differences, and integer
   SUM overflow. Missing-table/column examples remain valid counterexamples when
   the proposition permits them; concrete preconditions are tested, not assumed.
   Explicit schema inputs and custom generators remain available for SQL that
   cannot be extracted from the proposition and for arbitrary Lean predicates.
   Bounds, seed and candidate order are documented and controllable. No complete
   enumeration of all databases or all Lean propositions is promised.
4. **Plausible integration.** `Database` and `Value` have the sampling/shrinking
   support that Plausible needs, with a documented way to use it for Lean claims
   outside the SQL notation. The SQL checker reuses these samplers rather than
   maintaining a second unrelated candidate generator. Plausible search is
   untrusted. Its ordinary tactic admits a goal when sampling finds no failure;
   that behavior is never used to implement the SQL checker's proved result or
   `sql_refute`. Pin a compatible dependency and keep it out of the model and
   conformance runner.
5. **Replayable evidence.** A reported SQL counterexample includes its database
   construction, parameter values, relevant environment and observed outputs,
   plus a SQL script that the pinned `sqlite3` can replay. The replay recreates
   the witness and runs the original claim's SQL with the specified bindings; it
   does not replace a query with its expected answer. Validate reconstruction and
   observations, including quoting, BLOBs, SQL NULL and case-sensitive text.
   An unavailable or unmodeled observation cannot be presented as a native SQL
   failure. Search may return unknown when it cannot certify/replay a candidate.
   Arbitrary Lean predicates still get a checked Lean witness and a replay of
   their database; a non-SQL predicate is not falsely described as a SQL query.
6. **Automatic checking.** Elaborating a theorem statement that mentions SQL
   invokes the same bounded check by default. A certified counterexample is an
   error at that statement, including when its proof is still `sorry`. This
   diagnostic must not use the theorem being checked, its `sorry`, or an assumed
   proof of the claim as evidence. No unrelated theorem is checked merely because
   the library is imported. `sql.check` disables the automatic check, and
   `sql.checkBudget` bounds its work. Cancellation or timeout stops the search
   without an error alleging that the claim is false. Ordinary elaboration and
   the user's proof continue to have Lean's normal behavior.
7. **A regression example is usable.** The counterexample diagnostic offers the
   guide's "add as a regression example" code action, producing an explicit
   `sql_refute` witness that checks in a subsequent build without a random
   search. A successful proof search offers its checked proof script rather
   than telling the user to trust the search. Rechecking either artifact uses
   the same proposition that was checked originally.
8. **Clear boundaries.** Candidate generation, certification and display/replay
   have separate contracts. Only certification determines proved/false. The
   surface owns Lean elaboration and Plausible; SQL semantics remain in the
   model. Extend existing query/result laws when required to certify a witness,
   rather than copying the statement interpreter into the surface.

## Tests and acceptance

- Nix-selected surface fixtures exercise all three command results and both
  tactic modes. Use false universal `Holds`/`Empty`/`Fails` claims, an S4
  `Succeeds` claim, parameterized claims and a plain Lean predicate on databases.
  Also check true claims, unsatisfied preconditions, invalid supplied witnesses,
  unsupported/undecidable observations and exhausted search budgets.
- Fixed seeds or explicit candidate sequences find duplicate `NOCASE` values,
  the distinct non-ASCII case example, and two integer values of
  `4611686018427387904` whose SUM overflows. Fixtures name their assumptions so
  a missing table cannot substitute for the intended data counterexample.
- Check validity of generated and shrunk databases. Shrinking must keep a
  certified counterexample; a failed candidate is discarded, not admitted.
- Compile the produced explicit witnesses and audit their axiom dependencies:
  reject `sorryAx`, `ofReduceBool`, `_native`, and any proof obtained from the
  theorem under inspection. Include a malicious or incorrect candidate result
  to establish that certification, not the searcher's claim, controls acceptance.
- Replay emitted SQL under pinned native SQLite and compare reconstruction and
  observations. Include strings with quotes, NULL, BLOB and bound parameters.
  Exercise SQL error and `Output.unmodeled` distinctions without asserting that
  a model restriction is a native SQLite error.
- Test automatic checks and code actions through Lean's editor protocol as well
  as batch compilation: source range, cancellation, budget, disabled option,
  an unrelated theorem, and applying/rechecking the suggested regression example.
  Avoid wall-clock performance assertions that depend on machine scheduling;
  record responsiveness measurements and test explicit cancellation/budget paths.
- The Plausible compatibility build uses the repository's pinned Lean compiler.
  Test our instances/integration, not the dependency's own test suite. Existing
  layer tests continue to exclude new dependencies from the model and runner.
- Register every fixture in its actual Nix suite. Each coherent commit has its
  targeted checks and independent review. At each part boundary run
  `just test-full` and `just verdict`; at task end run `just test-nix` and
  `just test-scheduled-checks`. The owner instruction dated 2026-10-24 is recorded
  in [the build-boundary status](20261024-text-build-boundaries.status.md),
  including its source and exact text. All subprocess tests have timeouts.
- No model behavior, judge claim, corpus or lock changes are planned. Frozen
  predictions remain byte-identical. Any necessary semantic change is a separate
  model task and a specification finding before implementation continues.

## Parts and constraints

Three acceptance parts: the samplers and explicit certified witnesses; the
shared search and `#sql_check`; automatic checking and regression code actions.
The full task remains open until all outcomes and tests are satisfied.

S4's completed task and final interfaces are published in
[PR #244](https://github.com/vihren-dev/sqlite-verifier/pull/244), completion
`70705018e81bcd9f7159d107ec0f042e2ed8ef14`, with checked source
`24ca8b4c9635ee14f3235001dc86d7315ac514ac`. The task is
`plans/20261024-surface-s4.task.md`, outcomes 7 to 9; owner decisions 2 and 3
are in its companion status. `Success.lean`, `ProgramSuccess.lean`,
`ScriptSuccess.lean` and `QuerySuccess.lean` provide the final interfaces.
Use that success predicate and its universal-branch semantics: a program's canonical `db.run` result is
not a proof about every branch of `Output.oneOf`. S4 also checks the actual
raw continuation receiving `oneOf`, as well as every continuation receiving
concrete `rows`. A witness of failed success names a complete environment and
the actual run or permitted concrete continuation that fails. A raw Lean
continuation failure is not presented as a native SQLite statement failure.
A result
under `Env.default` alone cannot refute success over complete environments.
`Sql.decidableSucceedsFrom`, `Succeeds.not_of_failure` and `Succeeds.send_iff`
support concrete failure certification without changing the claim's meaning.

The guide's `sql_auto` ordering depends on S6. Until S6 exists, use the available
checked proof primitives without giving missing tactics a substitute meaning;
state the current capability in the guide. S6 supplies the complete automation
and its examples to the same checker.

Plausible's `v4.34.0` tag names Lean 4.34.0; this repository uses 4.34.1. Its
compatibility must be built, not assumed. `main` currently names a release
candidate and is not the dependency to adopt. Source references:
[toolchain](https://github.com/leanprover-community/plausible/blob/v4.34.0/lean-toolchain),
[Testable](https://github.com/leanprover-community/plausible/blob/v4.34.0/Plausible/Testable.lean),
[tactic behavior](https://github.com/leanprover-community/plausible/blob/v4.34.0/Plausible/Tactic.lean).
Lean 4.34.1 has command-linter hooks in `Lean/Elab/Command.lean`; their existence
is not evidence that all required editor behavior already works.
