## Outcome

1. **Definitions.** `CREATE TRIGGER [IF NOT EXISTS] name BEFORE|AFTER INSERT|UPDATE [OF
   columns]|DELETE ON table [FOR EACH ROW] [WHEN condition] BEGIN statements END` on a table,
   whose statements are `INSERT ... VALUES`, `UPDATE`, `DELETE` and `SELECT` (SQLite's grammar
   has no `DEFAULT VALUES` in a trigger, a syntax error), and `DROP TRIGGER [IF EXISTS] name`. `DROP TABLE` drops the table's triggers.
   Trigger names have a namespace of their own, apart from tables and indexes. The errors are
   SQLite's: `no such table: main.%s` for a missing table, `trigger %s already exists`,
   `cannot create trigger on system table`, and `no such trigger: %s`.
2. **When a trigger runs.** For each row that a write changes, in the write's row order:
   the `BEFORE` triggers run after the row's values are computed and checked against the
   rowid alias (`datatype mismatch`) and the types of a `STRICT` table (`cannot store ...`), and
   before its NOT NULL, CHECK and unique checks; the `AFTER` triggers run after the row is
   written and after the foreign-key actions of the row. Of the triggers of one time
   and event, the one created last runs first. `UPDATE OF` columns runs only when the `SET`
   list names one of them. `WHEN` is evaluated for each row; NULL and false skip the trigger.
3. **NEW and OLD.** The statements and `WHEN` read `NEW` (INSERT and UPDATE) and `OLD` (UPDATE
   and DELETE) as the row's values: `NEW` with the column affinities applied, and in a `BEFORE
   INSERT` trigger `NEW.rowid` is -1 while SQLite has not assigned the rowid. A body statement
   runs with the conflict algorithm of the triggering statement when it has one, else with its
   own. A name that the body or `WHEN` cannot resolve, such as `OLD` in an `INSERT` trigger or
   a missing table, is a prepare error of every write that would run the trigger, as SQLite
   prepares a trigger's program with the write.
4. **RAISE.** `RAISE(IGNORE)` ends the row: the rest of the trigger, the triggers after it
   and, in a `BEFORE` trigger, the row's own write; the statement goes on with the next row.
   `RAISE(ABORT, message)`, `RAISE(FAIL, message)` and `RAISE(ROLLBACK, message)` fail the
   statement as a constraint failure with that algorithm. `RAISE` outside a trigger is
   SQLite's prepare error `RAISE() may only be used within a trigger-program`.
5. **Nesting.** A trigger's statements fire the triggers of the tables that they write. With
   recursive triggers off, SQLite's default and the only setting that the slice models, a
   trigger does not run while it already runs; a write nested deeper than the trigger depth
   limit is not described. Rows that `REPLACE` deletes fire no `DELETE` trigger. The
   foreign-key actions of slice 4 fire the triggers of the child table; the implicit `DELETE` of
   `DROP TABLE` fires none. The change count of a statement counts its own rows only.
6. **Restrictions.** A `TEMP` trigger, an `INSTEAD OF` trigger (it needs views), a profile
   with recursive triggers on, and a `BEFORE` trigger that writes the table of its own
   `UPDATE` or `DELETE` (SQLite documents the result as undefined) stay restrictions or
   frontend refusals.

## Measurement

Over the local verdict after slice 4 (2026-10-21): 416 cases of v5 and 271 of v4 that are out
of scope create a trigger. Of them, 148 of v5 and 66 of v4 use none of the forms that stay out
of scope (views, `INSERT ... SELECT`, `TEMP`, `ALTER TABLE ... RENAME` or `DROP COLUMN`,
recursive triggers, `INSTEAD OF`, compound `SELECT`, other pragmas, `WITH`, `ATTACH`,
`EXPLAIN`): 106 of v5 use an `AFTER` trigger, 74 a `BEFORE` trigger, 33 `WHEN`, 22 foreign
keys, 13 `ON CONFLICT`, 12 `REPLACE`, 10 `RAISE` and 3 `UPDATE OF`. The counts are lexical,
so they are upper bounds.

## Key points

- **Bodies resolve when a write is prepared.** Natively, `CREATE TRIGGER ... BEGIN INSERT
  INTO nosuch VALUES (1); END` succeeds, and a later `DELETE FROM t WHERE id = 99` on its
  table fails at prepare with `no such table: main.nosuch`, also when no row matches; `OLD` in
  an `INSERT` trigger fails the same way. So the catalog keeps a trigger's syntax, and the
  resolution of each write resolves, against the catalog at that point, every trigger program
  that the write may run, and those of their statements in turn, each program once per
  statement as SQLite's `getRowTrigger` caches it. A resolved statement cannot hold resolved
  statements without one nested type; a list of programs that statements name by index, as
  slice 1 does for subqueries, avoids it.
- **`NEW` and `OLD` are an outer row.** They are cells before the body statement's own cells,
  by the mechanism of slice 1's correlated subqueries: resolution gives their positions.
- **The records name the schema's triggers in name order.** The recorder reads the schema
  with `SELECT ... FROM sqlite_schema ORDER BY type, name`, so a case whose setup creates two
  triggers of one table, time and event does not record which runs first. Such a pair in the
  starting schema is a restriction of the undecided registry; triggers that the script itself
  creates have a known order.
- **Writes with triggers run row by row.** Slice 4's row work (`ForeignKeyRows.lean`)
  already processes a write's rows in SQLite's order with nested writes for the actions; a
  write with a trigger takes the same path, also with foreign keys off. A row that an earlier
  trigger deleted is skipped, as SQLite's `OP_NotExists` skips it.
- **Checked natively**, over `t(id INTEGER PRIMARY KEY, v)` with `AFTER INSERT` triggers `a`
  then `b` and a `BEFORE INSERT` trigger `c` that log `NEW.id`: `INSERT INTO t VALUES (NULL, 1),
  (NULL, 2)` logs `c -1`, `b 1`, `a 1`, `c -1`, `b 2`, `a 2`, and `changes()` is 2. A newer
  `AFTER INSERT` trigger with `SELECT RAISE(IGNORE) WHERE new.v = 9` keeps the row 9 and runs
  neither `b` nor `a` for it; a `BEFORE INSERT ... WHEN new.v = 8` with `RAISE(IGNORE)` skips the
  row 8 and inserts the next row. An `AFTER UPDATE` trigger that updates its own row runs once
  (100 becomes 101). `BEFORE INSERT` reads `typeof(new.a)` as `integer` for `'5'` into an
  `INTEGER` column. A `BEFORE INSERT` trigger with `RAISE(IGNORE)` skips a row with a NULL for an
`INTEGER NOT NULL` column, but `'x'` for an `INTEGER` column of a `STRICT` table is `cannot store
TEXT value in INTEGER column s.a` and `'abc'` for an `INTEGER PRIMARY KEY` is `datatype mismatch`.
`INSERT ... DEFAULT VALUES` in a trigger body is a syntax error. `INSERT OR REPLACE` fires no
`DELETE` trigger; a cascade of a parent's
  `DELETE` fires the child's `AFTER DELETE` trigger. `RAISE(FAIL, ...)` in the `AFTER INSERT`
  trigger of the second of three rows keeps the first two rows. A table and a trigger may have
  the same name, and `DROP TABLE` drops the table's triggers.
- **Files.** The frontend `belay/sqlite/syntax_definitions.py` and `syntax_writes.py` (the new
  statements and `RAISE`), `Resolution/Syntax.lean`, `Resolution/Catalog.lean` (trigger
  objects), `Resolution/Resolve.lean` and the write resolvers, `ForeignKeyRows.lean`,
  `ForeignKeyWrites.lean` and `StatementStep.lean`, and every exhaustive match over the syntax
  and resolved statement types.
