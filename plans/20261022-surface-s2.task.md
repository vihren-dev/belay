## Scope

A user builds a database with `db!`, writes scripts with `sql`, runs them with `db.run`, sees
results with `#eval` and `#sql`, and proves facts about one database with `decide`. A
`Database` carries its proof of `Database.Valid`, so its facts need no hypothesis. The model
gets the work that this needs (ADR 0017, D3, amended): the output of each statement, and a run
that resolves each statement when it runs and continues after an error.

Out of scope, each recorded in ADR 0017, "Deferred, with their triggers", or in D1:
parameters and programs (S3), `Env` and its clock (S3), the native evidence for the statements
after an error, the functions that read the connection or random values, `pragma_table_info`,
the theorems that replace the run's check (ADR 0022, slices 2 to 4), and the lemmas of `Holds`,
`Empty` and `Fails` (S4).

## Outcome

1. **The output of each statement is in the model.** The model computes, for each statement
   that runs, its rows, its number of changes, its result code and every result that SQLite
   may give for it. These are today's `statementOutput`, `possibleOutput` and `primaryCode` of
   the conformance package, which then uses the model's. The conformance package keeps no copy.
2. **A run that continues after an error.** The model runs a script statement by statement: it
   resolves each statement against the state at the time that it runs (catalog, open
   transaction and the foreign-key setting), runs it, gives its output, and continues after an
   error. Inside a transaction, an error leaves the transaction open, as in SQLite, except a
   constraint failure under `OR ROLLBACK`, which rolls the transaction back and closes it
   (`SqlState.failed`). A statement that the model does not describe when it runs, or that does
   not pass the model's support check (`runStatement`'s `ready`), ends the run with the model's
   restriction. A statement that reads the clock (`Resolved.Statement.readsClock`) is such a
   statement in S2. A theorem states that, for a script that `resolve` accepts, the new run and
   `runSqlFrom` give the same outputs and the same state for each statement up to and including
   the first error, or up to the statement before the first one that ends the new run, whichever
   comes first.
3. **The surface's values.** `Value` is the model's value. `Value.compare`, `Value.truth` (with
   `Truth`: true, false, unknown), `Value.store`, the coercions from integer, string and decimal
   literals, and the lemmas `Value.truth_and`, `Value.compare_null` and
   `Value.store_integer_text`, each over the model's own definition (no second copy).
4. **The surface's databases.** `Database` holds a model database and its proof of
   `Database.Valid` under the pinned profile; `Database.Raw` is the model database, and
   `db.raw` gives it. `db.notNull`, `db.check`, `db.unique` and `db.rowid_unique` read the
   proof, so they need no hypothesis. `Database.empty`, `db.catalog`, and `db.rows name`, which
   gives `none` for a database without that table. `Database.Valid`, its atoms,
   `Database.Admitted` and `Database.ForeignKeysHold` are the model's (ADR 0022, slice 1).
5. **Scripts.** `sql r"..."` gives a `Script`: the statements as the translation gives them,
   parsed at elaboration; SQL that does not parse, or that the translation refuses, is an
   elaboration error at its position. `p ++ q`, `Script.empty` and the monoid laws.
6. **Outputs and runs.** `Output` has `rows`, `done`, `error`, `oneOf` and `unmodeled`, as the
   guide's table says. `db.run s` gives a `Run` with `outputs`, `db` and `start`; a query's
   output comes from every result that SQLite may give: one result gives `Output.rows`, in the
   guide's normal form, and more than one gives `Output.oneOf`. A `Run` also keeps the state of
   the connection at its end: whether a transaction is open, with the database at its start.
   `db` is the database that the connection sees. `Script.runUntilError` as the guide states it.
   `Script.run_append` in two forms: over the state of the connection, where `q` continues from
   the state that `p` left, and `q` does not run after an `Output.unmodeled` of `p`; and the
   guide's form over `(db.run p).db`, for a `p` that ends outside a transaction and has no
   `Output.unmodeled`. The run decides `Database.Valid` for the
   database at its end, and the decision is the proof of the `Database` that it gives; when the
   result is not valid, its outputs end with `Output.unmodeled`, which says so, and its database
   is the one at its start (ADR 0022, D5, amended). `Database.Raw.run` runs a script on a plain
   database and gives the model's result without the check.
7. **`sql!` and `db!` resolve at elaboration.** `sql! db r"..."` resolves the text against `db`,
   and `db!` runs its text on the empty database. A resolution error, a restriction of the model
   and a prepare error such as `no such column: nmae` are elaboration errors at the name, with
   the message that SQLite gives. A statement of `db!` that fails is an elaboration error at
   that statement, with SQLite's message.
8. **`db!` gives a `Database`.** It decides `Database.Valid` for the database that it builds,
   and the decision is the proof that the `Database` holds. A result that is not valid is an
   elaboration error that names the atom that fails.
9. **`Holds`, `Empty` and `Fails`** for one database, as the guide's "Queries as propositions"
   defines them, each decidable, so that `decide` proves them, or their negation, for a
   concrete database. `q` is a script of one read-only statement; the elaborator checks it
   where the guide says so.
10. **`#sql db r"..."`** prints the output of each statement in the editor; rows as a table with
   the column names, as the guide shows.

## Tests

- **The guide's examples.** A Lean file in the surface's suite holds every example of the
  sections in scope, the examples of `Output.oneOf` included, as the guide writes them; each
  `#eval` is checked with `#guard_msgs`, and each `decide` proof checks.
- **Errors at their positions.** With `#guard_msgs`: a syntax error at its token; `sql!` with a
  misspelled column and with a missing table, at the name; `db!` with a statement that fails
  (a NOT NULL column without a value), at the statement; a form that the translation refuses.
- **The run.** Examples, checked by the kernel: a failed INSERT followed by a SELECT that sees
  the rows before it; an error inside a transaction followed by `COMMIT`; an `OR ROLLBACK`
  constraint failure inside a transaction, after which the transaction is closed and its earlier
  writes are gone; `BEGIN` in `p` and `COMMIT` in `q` of `p ++ q`; a statement that
  names a table that an earlier statement of the same script drops; `random()` and
  `CURRENT_TIMESTAMP`, each giving `Output.unmodeled`, with no output after it; `LIMIT 1`
  without `ORDER BY` giving `Output.oneOf`; a query without `ORDER BY` whose output is the same
  before and after an index is created.
- **Validity without hypotheses.** Examples that use `shop.notNull` and the facts of the
  database after a run, with no hypothesis; a raw database whose constraints fail (as in
  `ValidityExamples.lean`) for which the check of outcome 6 gives no `Database`, and
  `Database.Raw.run` gives its result.
- **Queries as propositions.** The guide's `Holds` example on `shop`; an `Empty` and a `Fails`
  example, and `¬ Holds` for a query that fails, each by `decide`.
- **The agreement theorem** of outcome 2 compiles.
- **No change of behavior.** The predictions of every frozen corpus are byte-identical to those
  before the task (`nix-build integrity/judge.nix -A predictions`, then `diff -r`).
- **The usual checks.** The layer test of the surface, the documentation inventory and
  `just test-full`.

## Key points

- **Outputs today.** `VerifierConformance/Outputs.lean` (`StatementOutput`, `statementOutput`),
  `PossibleOutputs.lean` (`possibleOutput`) and `Case.lean` (`primaryCode`: 19 for a constraint
  error, 20 for a datatype mismatch, 1 otherwise); `Pass.lean` (`passFrom`) shows how they are
  computed for one statement with `runStatement` and `advanceWith` (`StatementStep.lean`).
  `Outputs.lean` imports only the model; `Case.lean` imports test-only modules.
- **Resolution assumes that earlier statements succeed** (`Resolution/Resolve.lean`, header):
  `resolve` folds the catalog over the whole script. After a failed `CREATE INDEX` or a failed
  `ADD COLUMN`, the catalog that `resolve` gives for the next statement is wrong; the new run
  takes the catalog of the database instead. `resolveStatement` resolves one statement against
  a `ResolveState`; the saved catalog of a transaction and the foreign-key setting come from
  the run's state. A restriction refuses a whole script in `resolve`; in the new run it ends
  the run at its statement.
- **Transactions.** `step` returns the database unchanged for `BEGIN`, `COMMIT` and `ROLLBACK`;
  `advanceWith` gives them their meaning, and an error inside a transaction leaves it open
  (`SqlState.failed`, `finish`). The new run must keep these meanings, not copy them.
- **Row order.** `Query.results` gives rows in scan order (`Table.scanRows`), not in the guide's
  normal form. `Resolved.Query.possibleOn` (`PossibleResults.lean`) gives every result, each
  tie group in normal form; the model root does not import it yet.
- **The clock.** `Resolved.Statement.readsClock` (`ClockReads.lean`) decides whether a statement
  reads the clock: `CURRENT_TIME`, `CURRENT_DATE` and `CURRENT_TIMESTAMP`, the date and time
  functions without a time value, a time value of `now`, `subsec` or `subsecond`, and a time
  value that is not a literal, such as a column, which can hold `now`. In S2 such
  a statement ends the run with `Output.unmodeled`; `Env` comes with S3.
- **`decide` and the kernel.** The guide writes `decide`; the model's examples use
  `decide +kernel`. Reals are bits read with `Float.ofBits`, which the kernel evaluates in Lean
  4.34.1. If plain `decide` cannot check the guide's examples, the guide must change to the
  tactic that does (the guide is fixed when it is wrong), and the status file records why.
- **The term that `db!` gives.** The model has no `ToExpr` for `Database`; it has one for
  `Value` and `Row` (`Codec.lean`) and for statements (`Codec/Resolution.lean`). A literal
  database and the run that builds it give different costs to later kernel proofs; measure.
  The proof in the term must be one that the kernel checks (the decision of the check), not a
  claim that elaboration checked it.
- **The cost of the check.** A run decides `Database.Valid` once, at its end; "keys unique"
  compares pairs of rows. The check decides whether the outputs end with `Output.unmodeled`,
  so a proof about the outputs evaluates it too. Measure the kernel time of the guide's
  examples with and without it.
- **Holds under every order.** `Holds` requires a row for every result that SQLite may give
  (guide open question 5), so it reads `Output.oneOf`, not one result.
- **Positions of names.** `Located` and `Span` are in the text package
  (`Translation/Located.lean`); nothing maps a restriction's path to a span yet (the Python
  `belay/sqlite/located.py` did). A prepare error carries a name but no path.
- **Two definitions of one thing.** Three-valued truth is written inline in `Expr.evaluate`
  (`ExprEval.lean`); `Value.truth` must be the definition that the evaluation uses, or have a
  theorem that they agree. The same holds for `Value.compare` (`compareValues`) and
  `Value.store` (`storeValue`).
- **Names.** The surface's names follow ADR 0016 (`Belay.Sqlite`); a model name that the
  surface gives again is the same declaration, not a wrapper with another meaning.
- **Files under 200 lines,** Verso docstrings, and plain words for every proposition.
