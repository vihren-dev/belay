## Outcome

1. **Forms.** `INSERT INTO t [(columns)] VALUES rows` followed by one or more clauses
   `ON CONFLICT [(columns)] DO NOTHING` or `ON CONFLICT [(columns)] DO UPDATE SET
   assignments [WHERE condition]`, with or without `RETURNING`, is admitted. Only the
   last clause may omit its target (SQLite's parser error otherwise). A target is a list
   of plain column names. It matches a key when its columns, compared without ASCII
   case and in any order, are the columns of one `PRIMARY KEY` (also a rowid alias),
   `UNIQUE` constraint or unique index. A target that matches no key is SQLite's prepare
   error `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`.
2. **Refusals and restrictions.** A target with `COLLATE`, `ASC` or `DESC`, or with a
   `WHERE` clause, is refused by the frontend (SQLite accepts some of these; the model
   does not decide them). A clause without target with `DO UPDATE` on a table with more
   than one key is a model restriction (owner decision 2). `INSERT … SELECT`,
   `INSERT … DEFAULT VALUES` and `INSERT OR` stay refused.
3. **Rows in order.** The rows of `VALUES` are processed one at a time, in order, and a
   later row sees the rows that earlier ones inserted or updated. For each row:
   - the values take the column affinities, the defaults and the alias rules of slice 5b
     (a NULL alias takes the next rowid); a `datatype mismatch` fails the statement;
   - a NULL in a `NOT NULL` column fails the statement before any conflict handling;
   - the clauses are tried in written order: the first clause whose target key has a
     conflicting row handles the new row, and the keys of later clauses and untargeted
     keys are not checked for it; a clause without target handles a conflict on any key;
   - without a handling clause, the row is inserted and checked against every key; a
     conflict is the ABORT error of today.
4. **DO NOTHING** skips the row. **DO UPDATE** changes the one existing row of the
   conflict. Its assignments and `WHERE` read that row (by column name or the table
   name) and the proposed row as `excluded.c`, after affinity and defaults; for a NULL
   alias, `excluded.id` is the next rowid. A `WHERE` that is not true skips the row. The
   updated row may change any column, also a key or the alias (slice 5b rules: a
   non-integer alias is `datatype mismatch`); it is checked against `NOT NULL` and every
   key at once, and a failure is the ABORT error of the statement.
5. **Errors and atomicity.** Every failure leaves the database as before the statement.
6. **Output.** `RETURNING` returns, in row order, each inserted row and each updated row
   with its new values, and not the skipped rows. The change count is the number of
   inserted and updated rows.
7. **Verification target.** `Contract.lean` does not change; every UPSERT keeps
   `Conforms`, and an INSERT without clauses keeps its current semantics.
8. **Evidence.** Authored coverage cases agree with native SQLite 3.51.0 and have kernel
   proofs; each mutant below changes a verdict; the verdict counts of the claimed
   corpora do not go down.

## Tests

- Lean examples: DO NOTHING on a conflict and without one; DO UPDATE with `excluded`,
  with a `WHERE` that is true and one that is false; two clauses, where the first one
  whose target conflicts handles the row; a later row that conflicts with an earlier row
  of the same statement; a DO UPDATE whose new values conflict on another key (ABORT);
  the change count and the `RETURNING` rows.
- Proofs: every UPSERT keeps `Conforms`; an INSERT without clauses has the semantics of
  today.
- Authored coverage cases (native SQLite as the oracle): each form of the outcome; a
  target in another order and case; a target that matches no key (prepare error); a
  composite key target; a rowid alias target, also with a NULL alias; `excluded` of a
  column with affinity and of an omitted column with a default; `WHERE` true, false and
  NULL; a row that conflicts on a targeted and an untargeted key; clause order with two
  targeted keys; a clause without target after targeted ones; `NOT NULL` before conflict
  handling; DO UPDATE that changes the alias and a key, with and without a new conflict;
  `RETURNING` and `changes()`; the restriction of a no-target DO UPDATE on two keys.
- Mutants, each changing the verdict of an authored case: DO UPDATE of the first row of
  the table instead of the conflicting row; `excluded` without affinity; the clause
  order ignored (the last matching clause handles the row); the untargeted keys checked
  before the target key; the rows checked only at the end of the statement instead of
  in order; a skipped row counted in `changes()`; the DO UPDATE result not checked
  against the other keys.
- Frontend tests: the translated forms, and the refusals of item 2 at their source
  range.

## Key points for the implementer

- **Frontend.** `belay/sqlite/syntax_writes.py` `insert` refuses the `upsert` node of the
  parse tree today, except for a bare `RETURNING`. The grammar is in
  `parser/upstream/parse.y` (`upsert`, `returning`); the clauses are a right-nested
  list. `tests/syntax_queries_test.py` has `test_upsert_stays_refused`.
- **Resolution.** `Resolution/Writes.lean` resolves INSERT to
  `Resolved.Statement.insert` (`Resolution/Resolved.lean`), with the rows already as
  stored values and the table's keys; UPDATE resolves its assignments and filter as
  expressions over the row. A DO UPDATE needs both: expressions over the existing row
  and an `excluded` row. Query evaluation (`QueryEval.lean`) already reads several
  named sources.
- **Execution.** `SqlExecution.lean` `insertOutcome` inserts all rows, then checks the
  keys once (`checkedWrite`); `LiteralData.inserted` and `RowUpdate.updated` build rows.
  UPSERT needs a check per row and the first conflicting row of a key
  (`LiteralData.keyEqual`, `keyCellsEqual`). The Laws (`Laws.literal_cases`) and the
  preservation proofs (`WritePreservation.lean`, `UpdatePreservation.lean`,
  `AliasPreservation.lean`) unfold `insertOutcome`; keep a statement without clauses on
  today's path so that its proofs stay.
- **Readiness.** `statementReady`, `insertReady` and `updateReady` are the obligations
  of a write; DO UPDATE values need the same bounded-rowid and assigned-column
  conditions as UPDATE.
- **Outputs.** `packages/verifier-conformance/VerifierConformance/Outputs.lean` computes
  `RETURNING` and the change count of INSERT from the appended rows; with UPSERT, updated
  rows count too, and they keep their place in the table.
- **Row-dependent keys.** Amendment 1 restricts an UPDATE `SET` of a key that reads the
  row, as SQLite's order of rows decides the result. DO UPDATE changes one known row per
  proposed row, in `VALUES` order, so it does not need that restriction.
- **File size.** `SqlExecution.lean` is near 200 lines; UPSERT execution belongs in its
  own file.
- **Kernel and mutant cost.** Keep authored cases small; measure the mutant and model
  suites after the change.
